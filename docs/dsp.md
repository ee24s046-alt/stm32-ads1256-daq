# Signal processing

Multirate processing and spectral estimation running live on the acquisition
pipeline, not as a post-processing step on captured files.

Everything here is implemented in `firmware/lib/` and runs on the STM32; the
host carries an independent reference implementation of the same maths, and the
two are checked against one generated vector. That cross-check is the point —
see [Verification](#verification).

---

## 1. Why there are two acquisition modes

The DSP chain only makes sense in one of them, and the reason is a timing fact
rather than a preference.

| | `DAQ_MODE_MUX4` | `DAQ_MODE_WIDEBAND` |
|---|---|---|
| Channels | 4 differential pairs | 1, multiplexer parked |
| MUX changes | every conversion | none |
| Settling penalty | 4 conversion periods | **none** |
| `/DRDY` period | 133 µs | **33.3 µs** |
| Sampler budget used | 61.4 µs / 46 % | 26.8 µs / **80 %** |
| Delivered rate | 1875 scans/s | 30 000 samples/s |
| After M=4 decimation | — | **7500 samples/s** |
| Wire rate | 45 kB/s | 180 kB/s |

The ADS1256's decimation filter is a 5th-order sinc. Changing the multiplexer
forces a `SYNC`/`WAKEUP` restart, and the first fully settled result then takes
the filter's settling time — 0.13 ms at DRATE = 30 kSPS, exactly four conversion
periods. Park the multiplexer and that penalty disappears: every conversion is
usable and `/DRDY` arrives at the full 30 kSPS.

**This is the only regime in which the published DSP numbers are coherent.**
M = 4 from 30 kSPS gives a 3750 Hz output Nyquist, which is what makes a 3.5 kHz
anti-alias corner a meaningful specification. Applying M = 4 to the muxed mode's
1875 Hz per-channel stream would put the output Nyquist at 234 Hz, and a 3.5 kHz
corner there would alias everything above 234 Hz back into the band.

Switch with `mode wide` / `mode mux` on the debug UART.

## 2. The decimation filter

Generated by [`tools/design_filter.py`](../tools/design_filter.py), which emits
`firmware/include/fir_coeffs.h` and `host/ads1256_host/fir_coeffs.json` from one
specification. Re-run it to change the design; do not hand-edit either output.

```
taps                      68  (17 per polyphase branch)
rate              30000 Hz -> 7500 Hz   (M = 4)
-3 dB corner            3501 Hz
passband droop          0.06 dB, DC .. 3 kHz
alias rejection         55.6 dB worst case into DC .. 3 kHz
```

### Where the stopband edge comes from

The stopband edge is **not** the output Nyquist, and getting this wrong is
expensive. What matters for a decimator is which input frequencies fold into the
*band of interest* after downsampling. Images land at `k·7500 ± f`, so with the
band of interest declared as DC–3000 Hz:

- **4500–7500 Hz folds into 0–3000 Hz** — must be ≥ 40 dB down
- 3750–4500 Hz folds into 3000–3750 Hz — declared don't-care

Specifying the stopband at 3750 Hz instead of 4500 Hz shrinks the transition
band by 6×, and the tap count grows in proportion: **68 taps instead of about
660**. Over-specifying an anti-alias filter is not free and buys nothing.

### Design choices

**Hamming window, not Blackman.** ~53 dB stopband for a given transition width,
which clears the requirement with margin, at ~40 % fewer taps. Blackman's extra
depth would be spent on a requirement nobody has.

**Not Parks-McClellan.** An equiripple design would hit the same spec in about
45 taps, but it needs SciPy and the saving is 23 MACs per output at 7.5 kHz —
172 kMAC/s on a part that does one MAC per cycle at 168 MHz. Not a trade worth a
dependency.

**Q15 taps summing to exactly 32768.** Unity DC gain, not approximately: a
0.3 % gain error here is indistinguishable downstream from a failed offset
calibration. Quantisation preserves symmetry as well as the sum — only the first
half is quantised and the correction applied there, then mirrored. Dumping the
rounding residual onto the largest tap (the obvious approach) fixes the sum and
silently destroys linear phase.

**int64 accumulator.** Input codes reach 2²³ and the tap sum is 2¹⁵, so the
worst case needs 38 bits before the shift. In int32 this overflows silently and
only on large signals — i.e. it passes every bench test done on a shorted input.
On Cortex-M4 the 64-bit MAC is a single `SMLAL`, so it is also free.

**Round-to-nearest, not truncate.** A bare `>>15` floors, biasing every output
by −0.5 LSB — a DC offset introduced by the filter on a chain whose purpose is
that DC offsets have been calibrated out.

### Why polyphase

The naive implementation filters every input sample and discards M−1 of every M
results: **68 × 30000 = 2.04 MMAC/s**.

Writing the tap index as `i = pM + k` splits the prototype into M branches of
N/M taps, each running on a subsequence at the *output* rate. Only the samples
that survive are computed: **68 × 7500 = 510 kMAC/s**. Exactly 4× fewer
operations for bit-identical output.

`tests/test_fir_decimate.c::test_polyphase_equals_naive` asserts that identity
against a deliberately-naive reference, because "it is mathematically the same"
is exactly the kind of claim that is quietly false after an off-by-one in the
branch indexing — and a permuted branch order still produces output that looks
like filtered data.

### The decimator is load-bearing

In wideband mode the sampler produces 30 000 samples/s. Streaming those raw
would be 720 kB/s, most of what USB full speed can sustain. Decimation takes it
to 180 kB/s. So the anti-alias filter is not an ornament on the data path — it
is what makes the mode fit on the link, and because it is a real filter rather
than "keep every 4th sample", it does that without folding 3.75–15 kHz into the
output band.

## 3. Spectral estimation

1024-point FFT, periodic Hann, 50 % overlap, **6 segments averaged** → one PSD
block per ~478 ms, per channel, round-robin.

### Averaging is what reduces variance. FFT length does not.

This is the part most often got wrong, so it is stated plainly and tested.

A single periodogram is a terrible estimator. Each bin is the squared magnitude
of one complex Gaussian sample, so its standard deviation **equals its mean** —
about 5.6 dB of scatter — regardless of transform length. A 16384-point FFT
instead of a 1024-point one buys 16× finer resolution and *exactly zero*
reduction in variance. There are simply more bins scattering.

Variance falls only by averaging independent estimates: with K averages it falls
as 1/K. Measured, by `ads1256 dsp`:

```
  1024-pt, 1 average  :  5.37 dB scatter
  16384-pt, 1 average :  5.56 dB scatter   <- 16x the resolution, no better
  1024-pt, 6 averages :  2.00 dB scatter   <- 2.7x better
```

The improvement is slightly short of √6 because 50 %-overlapped Hann segments
are not fully independent — the effective K is about 0.9 × 6.

`ads1256 dsp --plot dsp.png` draws the single periodogram against the averaged
estimate on the same data at the same resolution.

### Window details that matter

**Periodic Hann (divisor N), not symmetric (divisor N−1).** NumPy's
`np.hanning()` is the symmetric one, which is right for filter design and wrong
for spectral analysis of a continuing signal: it leaves a discontinuity between
consecutive overlapping segments. The host reference builds the window
explicitly rather than calling NumPy, and a test guards against someone
"simplifying" it back.

**The PSD normaliser is `fs · Σw²`, not `(Σw)²`.** The latter is correct for
reading a peak amplitude off a spectrum; using it for a *density* makes every
reading wrong by 1.76 dB — consistently, which is what makes it look like a real
measurement. Both implementations are checked by a Parseval test.

**Mean removed before windowing, not after.** A DC offset multiplied by the
window becomes a scaled copy of the window's own spectrum smeared across the low
bins, indistinguishable from real low-frequency content, dominating the noise
floor at exactly the frequencies the measurement cares about.

### Float FFT, fixed-point filter

Opposite choices, for opposite reasons.

A Q15 FFT must rescale by ½ at each of the 10 stages to avoid overflow, costing
10 bits of dynamic range — on a floor being characterised at 20 effective bits,
that is most of the measurement. The M4F's FPU has a 24-bit mantissa and no such
problem.

The usual objection to float in this firmware is that touching the FPU makes
FreeRTOS lazily stack 33 extra words on preemption. That objection does not
apply here: the metrics task is the **only** FPU user and sits at the lowest
priority, off the acquisition deadline path entirely. Nothing with a deadline is
ever preempted while holding FPU state. Had the metrics been folded into the
processor task — tempting, since it already has the samples — every preemption
by the sampler would carry that cost on a path with microseconds of margin.

A full complex transform is used on real input rather than the split-radix trick
that would halve the work: at one transform per 478 ms the saving is 0.03 % of
the CPU, against roughly double the code that has to be right.

## 4. Live metrics

| Metric | Window | Scope |
|---|---|---|
| RMS | 100 ms | all 4 channels, continuously |
| PSD | ~478 ms | one channel, round-robin |
| THD+N | ~478 ms | from the same averaged spectrum |

RMS runs on every channel because it is an int64 accumulate and a square root.
The PSD runs on one channel at a time because four simultaneous Welch
accumulators would cost 4 × (4 KB staging + 2 KB accumulator) = 24 KB of SRAM to
produce a result nobody reads four times a second. Each channel updates every
~1.9 s instead.

### THD+N, and its floor

Computed as everything outside a band around the fundamental, divided by
everything inside it, with 3-point parabolic interpolation to place the
fundamental between bins (bin spacing is 7.32 Hz; without interpolation a 1 kHz
tone reports as 998.5 Hz and looks like a clock error).

**The honest limitation:** a tone that does not land exactly on a bin leaks
through the Hann sidelobes, and that leakage is counted as distortion. With a
±8-bin fundamental band the floor is around −65 dB. A ±2-bin band — the Hann
main lobe, which is the obvious choice — puts the floor at **−33 dB**, and the
reading then measures the window rather than the signal chain. Below −65 dB you
need coherent sampling or a Blackman-Harris window for the THD path
specifically; Hann is kept because the PSD is the primary product.

**No tone, no number.** On a shorted input the "peak" is the luckiest noise bin,
and dividing noise by noise yields a confident-looking figure that means
nothing. Both implementations require the fundamental to hold more than half the
total power, and report `INT32_MIN` / `None` otherwise.

## 5. Pipeline placement

```
sampler    prio 4   30 kSPS raw                      (wideband)
   |  ring_raw
processor  prio 3   polyphase decimate 4:1 -> calibrate -> encode
   |  ring_tx  -> uplink          |  ring_dsp
uplink     prio 2                 metrics  prio 1   RMS / FFT / Welch / THD+N
                                     |  ring_meta
                                  uplink   prio 2   64 B and 1044 B records
```

The decimator runs in the processor task because it is per-sample, cheap and
deterministic. The FFT runs in its own task at the lowest priority because it is
a ~310 µs block that nothing with a deadline may ever wait on.

Metrics and PSD records add about 1.3 kB/s to a link already carrying
45–180 kB/s of samples: **under 3 % overhead** for a live view of the noise floor
that would otherwise need a capture to disk and a post-processing pass.

See [protocol.md](protocol.md#record-types) for the wire format.

## 6. Verification

Nothing above is asserted without something checking it.

**One source of truth.** `tools/design_filter.py` emits the C header, the JSON
the host loads, and a golden input/output vector. The firmware test
(`tests/test_fir_decimate.c`) and the host test (`host/tests/test_dsp.py`) assert
the *same* vector. Two independent implementations agreeing bit for bit on
generated data is what makes "the DSP on the device is correct" a check rather
than a claim.

**What the tests cover:**

| Claim | Test |
|---|---|
| Polyphase == filter-then-discard, bit-identical | `test_polyphase_equals_naive` (C) |
| 4× fewer MACs | `test_mac_count_is_four_times_cheaper` (C) |
| >40 dB alias rejection, measured | `test_alias_rejection` (C), `test_alias_rejection_exceeds_40_db` (Py) |
| …and a control that fails it | `test_no_filter_would_fail_this` (C), `test_naive_downsampling_fails_the_same_case` (Py) |
| Unity DC gain and linear phase | `test_taps_are_unity_dc_gain` (C), `test_taps_are_symmetric_and_unity_dc_gain` (Py) |
| Fixed-point path exact to ½ LSB | `test_fixed_point_arithmetic_is_exact_to_half_an_lsb` (Py) |
| FFT correct (impulse, DC, tone, Parseval) | `test_spectral.c` |
| Window normaliser is Σw² | `test_hann_window_power_normaliser` (C), `test_welch_normaliser_satisfies_parseval` (Py) |
| FFT length does not reduce variance | `test_longer_fft_does_not_reduce_variance` (Py) |
| Averaging does | `test_averaging_reduces_variance_fft_length_does_not` (C), `test_averaging_does_reduce_variance` (Py) |
| THD+N tracks real distortion | `test_thdn_degrades_with_distortion` (C), `test_thdn_tracks_added_distortion` (Py) |
| THD+N refuses to report on noise | `test_thdn_refuses_to_report_on_pure_noise` (C) |
| Mixed-record framing at any chunk size | `test_decoder_frames_a_mixed_record_stream` (Py) |

```bash
# the firmware's own DSP, compiled natively under ASan + UBSan
cmake -B build-host -DDAQ_BUILD_HOST_TESTS=ON && cmake --build build-host
ctest --test-dir build-host --output-on-failure

# the host reference and the cross-checks
cd host && python -m pytest -q

# the demonstration, with numbers and a plot
ads1256 dsp --plot docs/img/dsp-demo.png
```
